## Architecture decisions

- TML AI uses AI Elements and an injectable streaming adapter through a same-origin CAPTCHA-verified TanStack server route; Gemini keys stay server-only, conversations stay in React state, and the only accepted mode is community Q&A; retrieval uses a publishable client reading only the dedicated approved-public document table. Community output is a validated verbatim excerpt with source/date, so model-generated claims never become public organizational facts.

- Keep public verification domain types, demo records, and Zod validation in one client-safe module so Supabase can replace the data source later without rebuilding the UI.
- Public content groups use typed accessors in src/lib/data/* so data sources can change without UI changes.
- Recruitment (periods, positions, topics, questions, applications) lives in Supabase tables; public submissions go through a server function that re-validates every rule with the admin client, so the browser is never trusted.
- Applicant files upload via server-issued signed URLs into a private bucket; only holders of candidates.edit, or of candidates.view for one of the applicant's chosen departments, can read them (CV and files attached to answers).
- Internal accounts are created and managed only through server functions that check the caller's matrix permission (members.edit) and rank before using the admin auth API; only admins may change or even see the admin flag (the only role kept in user_roles; non-admins get only a neutral locked marker on accounts they cannot act on), there is no public sign-up, and suspended/disabled status is enforced with an auth ban so blocked users cannot sign in.
- Account, member profile, department/position and the admin flag are stored separately (member_accounts, members, user_roles) so each can change independently.
- Permissions come from a department × position matrix (`position_permissions`, 38 actions with own/all scope), one row set per department with no wildcard department, plus expiring personal grants, resolved only by `has_perm(action, dept)`; rank rules use `outranks()` / `can_assign_position()` (Co-founder > Trưởng Ban > Phó Ban > others), the admin flag bypasses both, and every matrix/grant change goes through admin-only RPCs that write `permission_audit_logs`, so RLS, server functions and UI read one source of truth.
- Tasks and contribution points change only through security-definer database functions (create/update/review task, adjust points) that write an append-only point history row; clients have read-only table access so points can never be edited directly.
- Member codes are assigned by a database trigger (join month + global running sequence), so every insert path gets a consistent code.
- Application status changes go through a security-definer function that snapshots the reviewer from the session into an append-only history, so reviewers cannot be spoofed or history edited.
- Public org chart reads leaders/counts only via the security-definer `public_org_chart()` function, which respects each member's `is_public` flag, so the members table never becomes publicly readable.
- Teachers are a separate table managed with teachers.edit, linked to HSK courses by teaching level, so courses can stay static until they move to Supabase.
- Course registrations (course_enrollments) must target a concrete HSK class or program and are submitted and reviewed only via server functions, so applicants never touch the table; course_settings now holds only per-level teacher assignments and never gates registration.
- Programs live in `courses` (soft delete, public reads published only); old level-only enrollments (no class/program) stay readable and reviewable one by one, but new ones are rejected by the server.
- Concrete HSK classes live in `hsk_classes` under fixed levels 1–6 (no levels table); enrollments link via course_enrollments.hsk_class_id and the server re-checks status and seats, so a class can be created without touching code.
- Programs (`courses` table) carry show_in_courses / show_in_activities flags so one record feeds both /courses and /activities without duplicates.
- AI onboarding plans are generated once by an authenticated server function and stored in `onboarding_plans` (read-only to managers and the member), so reopening a plan never spends AI calls again.
- Activities (soft delete) take public registrations only via a server function and a trigger writes append-only audit logs; programs are never copied in, /activities reads `courses.show_in_activities`.
- Certificates live in `certificates` (RLS on certificates.view / certificates.edit); public lookup only via security-definer `verify_certificate()` returning safe columns, and a trigger strips whitespace/uppercases codes so every insert path stores lookup-ready codes.
- Site UI text uses the typed dictionary in src/lib/i18n (vi/zh/en, Vietnamese on SSR then the stored choice after hydration), so new languages or strings need no library and never cause hydration mismatches.
- Certificate AI extraction only pre-fills the admin form via a server function checked on certificates.edit; nothing is saved until the admin confirms, so AI mistakes never reach public verification.
- HSK results live in `hsk_results` (RLS on hsk.view / hsk.edit, deleting only revoked rows); triggers compute totals/pass and append `hsk_score_audits`; public reads only via security-definer `verify_hsk()` (code+name or token), so scores can't be faked or enumerated.
- Admin menu and in-page buttons come from `my_permissions()` via `allowedSections()` / `can()` (section → matrix actions in `SECTION_ACTIONS`, admin flag sees all), so the UI hides exactly what RLS would refuse; the database stays the only real gate (the news trigger and `site_content_guard_publish` still block self-publishing).
- Public submit/lookup forms need a server-verified reCAPTCHA token; QR-token lookups skip it so QR links keep working.
- Member benefits (shared Premium accounts) live in `benefits`/`member_benefits` (RLS on benefits.manage); members read via definer RPCs only, so credentials never leak.
- Portal hostnames (main/join/member) are mapped in src/lib/domain.ts and enforced both in src/server.ts (first load) and the root route (client navigation), so one codebase serves all three portals and preview hosts never redirect.
- Shared HomeLink uses the domain helper for full-document navigation from satellite portals to the main homepage, so root landing redirects cannot trap Home clicks; main and preview hosts retain local router navigation.
- Professional advisors live in `department_advisors` + per-department `department_advisor_settings` (writes on departments.advisors), public reads via definer `public_dept_advisors()`, so advisor assignments never alter member profiles or grant permissions.
- Course–teacher assignments live in `course_teachers` (role + sort_order); `courses.teacher_id` is deprecated and only mirrors the lead, and teacher `status` drives `visible` via trigger so old readers keep working.
- Member profile writes follow the permission matrix: members RLS checks members.edit and the `members_guard_write` trigger blocks direct writes that touch a member of equal/higher rank, move a member into a department without members.edit, assign an equal/higher position, or edit protected columns (code, points), while definer functions and the service role keep their own checked paths.
- One task fan-out creates one `tasks` row per assignee (each reports evidence and earns points independently); each task is displayed as an individual card per assignee on the Kanban board so each member's status and progress can be moved and tracked independently.
- Admin settings, the own-tasks board, the contributions page and the feedback page open to every active member account via `withPersonalSections()` (`PERSONAL_SECTIONS` = tasks, contributions, settings, feedback; kept out of `allowedSections()` so module rules stay exact; blocked or account-less users get nothing extra), and users whose only sections are personal land on `/admin/tasks`. Without tasks.view the board shows only tasks assigned to the viewer (tasks RLS) and acts only through `member_update_task`; assignee names come from `getTaskPeople`, which resolves names only for tasks the caller can already read. Settings' personal blocks use only own-account RPCs (`my_account`, `update_my_profile` for the avatar only, `set_my_visibility`; names change only on the members page with members.edit) and Supabase Auth, so no new server path can touch other accounts.
- Feedback ("Nhận xét", `/admin/feedback`) lives in `feedbacks` with a private `feedback-screenshots` bucket; every active member sends a bug report / improvement idea / other comment as themselves (member id from the session) and reads only their own rows, while the Co-founder, admins and the Technology & Systems heads, deputies and advisors read and answer every row through the matrix action `feedback.review` (rows for executive/Co-founder and tech/Trưởng Ban, Phó Ban, Cố vấn chuyên môn). RLS keeps the visibility rule and the `feedbacks_guard_write` trigger keeps columns honest: a writer may fix their own submission only while it is `pending`, a reviewer may change only status, reply and resolution (never the writer's words), and `resolved_by`/`resolved_at` are stamped only when the status becomes `resolved` or `closed`.
- Admin system status comes from the admin-checked `getSystemStatus` server function, which reports only whether each integration's env vars are set (names, never values) plus a DB round-trip time, so admins can spot broken integrations without secrets ever reaching the browser.
- Class/program chat-group links live in `course_group_links` (written with courses.edit, readable with courses.view), never as columns on the publicly readable `hsk_classes`/`courses`, so group links reach only approved students by email.
- Admin UI is assembled from shared pieces in `src/components/admin/kit/` plus the admin sizes/variants of `ui/button` (`admin`, `admin-lg`, `admin-icon`, `destructive-outline`), so pages stop copy-pasting markup and one fix reaches every admin screen; public pages keep the original button styles. Every admin route (`src/routes/_authenticated/admin*.tsx`), every file under `src/components/admin/` and the course admin pieces are linted through `ADMIN_KIT_FILES` in `eslint.config.js`, where raw `<button>`, `<input>` (except `type="file"`), `<textarea>`, `<select>` and `<table>` are lint errors; only the kit itself is excluded, so new admin files are covered automatically. The only allowed escape is `// eslint-disable-next-line no-restricted-syntax -- <reason>` on full-surface hit areas (drop zones, card cover buttons) where kit buttons do not fit.
- A task can be edited, deleted, approved or sent back only by its assigner (`tasks.created_by`) or an admin, who must also hold tasks.edit for the task's department; `updateTask`, `review_task` and `delete_task` enforce it and the board mirrors it with `taskRights()`, so a lower rank can never rewrite or approve work someone else assigned. Rows with no `created_by` are admin-only.
- The contributions leaderboard is readable by every active member account only through the security-definer `points_leaderboard()` (safe columns of active members with an active login, now including `avatar_path`), so the members table stays scoped; the point ledger stays behind `point_transactions` RLS (own rows for everyone, departments with points.view), so members see only their own history.
- Member avatars live in the private `avatars` bucket, are signed in one batch with a 6-hour cache by `src/lib/avatars.ts` and drawn by the `MemberAvatar` kit component (initials when there is no image or it fails to load); every active member account may read that bucket because the leaderboard, members list, departments, tasks, benefits and the member dashboard show colleagues' photos, while only the owner may write it. `points_leaderboard()` and `my_department()` carry each member's `avatar_path` so those definer reads can show faces without opening the members table.
- Permissions are being simplified page by page to view / create / edit actions, and deleting always follows the page's edit action (no separate delete action); the recruitment page uses `recruitment.view`, `recruitment.create`, `recruitment.edit` (periods and their positions) and `questions.edit` (topics and questions), enforced by RLS on the four recruitment tables.
- The candidates page has `candidates.view` (profile, answers, CV and files; Co-founder, secretary and all of HR see every applicant, heads and deputies of other departments only those who chose their department), `candidates.edit` (full record, AI, status, notes, history; Co-founder, HR heads and deputies) and `candidates.convert` (Co-founder, HR heads and deputies); `candidate_applications` and its history are readable only with candidates.edit, and view-only users read the safe columns through the definer `candidate_profiles()` (scoped by their wishes), so internal notes and AI summaries never reach them.
- The members page has two actions: `members.view` (every member of every department, with phone, email and CSV export; every position) and `members.edit` (add, edit, move, hide/show, delete and manage login accounts; Co-founder, HR heads and deputies); rank rules still limit edits to strictly lower positions and never touch an admin account.
- The tasks page has `tasks.view` (the whole department's tasks; without it a member sees only tasks assigned to them), `tasks.create` (assign work) and `tasks.edit` (edit, approve / send back and delete tasks you assigned); heads and deputies hold all three for their own department and the Co-founder everywhere, while assignees start and report their own tasks through `member_update_task` with no action needed.
- The contributions page keeps the leaderboard open to every member, `points.view` for a department's point history (members always see their own rows) and `points.adjust` for bonus / penalty on strictly lower positions only (so nobody adjusts themselves); heads and deputies hold both for their own department and the Co-founder everywhere, while `points.attendance` (heads and deputies own, the Co-founder all) scores Google Meet attendance.
- The academic pages each have a view / edit pair (`courses.*`, `teachers.*`, `hsk.*`, `certificates.*`, all department-less): view is held by the Co-founder and every position of the academic department, edit (every write, deleting included, and certificate AI) by the Co-founder and the academic heads and deputies.
- Activities, photos and partners each have a view / edit pair (`activities.*`, `photos.*`, `partners.*`, department-less): view (activities with drafts, registrations and audit log, hidden photos, partners) is held by the Co-founder and every position of the translation, comms, finance, design and podcast departments, edit (every write, deleting included) by the Co-founder and those departments' heads and deputies.
- News uses `news.view` (every article) and `news.edit` (write and manage your own unpublished articles; review, publish, archive and edit articles whose author holds a strictly lower position), both held by the Co-founder and every position of the five media departments; the rank rule lives in the definer `can_review_news(author)` used by RLS, the `_news_guard` trigger and the UI (`news_reviewable_ids()`), so nobody reviews their own work and only admins review the Co-founder's.
- The departments page has `departments.view` (every member of the organisation reads every department's leaders, work channel and advisors) and `departments.edit` (work channel and advisors; heads and deputies for their own department, the Co-founder everywhere).
- After sign-in, `routeAfterLogin()` sends every active account (blocked and password-change cases aside) to `/admin`, so members whose only sections are members, departments and the personal ones (advisors, plain members) still open the overview instead of the member card; users whose only sections are personal continue to `/admin/tasks`, and the member card stays reachable from the admin menu.
- The content page keeps `content.edit` (read and edit drafts) for the Co-founder and every position of the comms and translation departments, and `content.publish` for the Co-founder only; the `site_content_guard_publish` trigger still blocks publishing without it.
- The leader card follows `members.is_leader`, which only admins set (plain SQL; `members_guard_write` blocks everyone else); leaders earn no points (`_apply_points` skips task points and refuses bonus / penalty / attendance) and `points_leaderboard()` leaves them out, while every new member starts at 0 points. One-time data maintenance (such as the 2026-11-08 blank reset of points and all history / audit tables) records a key in `maintenance_runs`, so re-running a migration never repeats it.
- Members link their own Google account once in Settings: the browser gets a Google ID token from Google Identity Services, and the `linkMyGoogleAccount` server function verifies it with Google (tokeninfo, audience = `GOOGLE_OAUTH_CLIENT_ID`) before storing `member_google_accounts` (one Google account per member, member taken from the session); the table has no client policies and members read or remove only their own link via `my_google_link()` / `unlink_my_google()`, so Meet attendance can match `users/{id}` without anyone typing or guessing IDs.
- Meeting attendance comes only from Google Meet and is scored per meeting, not per department: the server reads who was present from Google itself and calls the service-role-only `record_meet_attendance(_actor, …)`, which acts as the scorer (`auth.uid()` set for the transaction so has_perm and the point ledger see the real person) and stores one `attendance_sessions` row per Meet conference record (unique, meetings of at least 30 minutes); everyone present earns 2 points for a working meeting or 10 for a club-wide one (club-wide needs points.attendance on every department), hand-added members must be in a department the scorer covers and are kept in `manual_ids`, leaders are left out, and `adjust_points` refuses the old manual attendance kind. The browser only holds a short-lived Google access token (meetings.space.readonly, requested in the click so popups are not blocked) that the attendance server functions use to list conference records and re-read participants before scoring; nothing from Google is stored besides the session row.
